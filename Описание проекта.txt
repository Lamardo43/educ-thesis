# Техническое описание системы управления имитационными сервисами («заглушками»)

**Тема проекта:** Разработка автоматизированной информационной системы управления распределенной инфраструктурой имитационных сервисов для нагрузочного тестирования.

### 1. Назначение и концепция системы

Система предназначена для централизованного управления жизненным циклом имитационных сервисов (Java-приложений в форматах `.jar` и `.war`), используемых в качестве «заглушек» внешних интеграций при проведении нагрузочного тестирования. Программный комплекс позволяет автоматизировать процессы развертывания, контроля состояния и маршрутизации трафика, обеспечивая импортозамещение зарубежных решений (например, Tomcat).

### 2. Гибкая архитектура и масштабируемость

Система поддерживает два режима функционирования:

* **Локальный режим:** Все компоненты (управляющее приложение, БД, имитационные сервисы) работают на одном хосте.
* **Кластерный режим (Master-Slave):** * **Центральный узел (Master):** Выполняет функции управления, ведения базы данных и динамического проксирования запросов.
* **Подчиненные узлы (Slave):** Выполняют только запуск и остановку имитационных сервисов по командам Master-узла. Количество Slave-хостов не ограничено, что обеспечивает практически бесконечное горизонтальное масштабирование системы.



### 3. Функциональные механизмы и алгоритмы

Реализация системы предполагает использование следующих ключевых механизмов:

* **Управление процессами:** Запуск имитационных сервисов осуществляется через модуль `subprocess` (Python). Система поддерживает ввод пользователем произвольных параметров командной строки (JVM-аргументы, такие как `-Xmx`, `-Xms` и др.) для тонкой настройки запуска каждого сервиса.
* **Динамическая маршрутизация (Reverse Proxy):** Master-узел перенаправляет входящие запросы по URL-префиксу `/<mock_name>/` на соответствующий IP и порт, на котором запущен конкретный сервис. Это позволяет абстрагироваться от физических адресов и портов при обращении к заглушкам.
* **Механизм Rate Limiting (RL):** Настраиваемый вручную функционал ограничения интенсивности запросов. Система проксирования анализирует количество входящих запросов к сервису и, при превышении заданного пользователем порога (RPS), автоматически возвращает HTTP-ошибку **429 Too Many Requests**, предотвращая перегрузку инфраструктуры.
* **Автоматическое распределение ресурсов:** При работе в кластерном режиме система автоматически выбирает Slave-хост для запуска нового сервиса на основе анализа загруженности серверов (CPU/RAM).

### 4. Работа с данными и сохранение состояний

Информационное обеспечение системы базируется на реляционной базе данных (SQL):

* **Хранение PID:** Идентификаторы процессов (PID) запущенных сервисов сохраняются в БД для корректного управления ими (остановка, перезагрузка) без риска потери контроля над процессом при перезапуске основного приложения.
* **Персистентность состояний:** Система фиксирует текущее состояние каждой заглушки (активна/остановлена). При запуске управляющего приложения (после перезагрузки сервера или сбоя) реализуется алгоритм автоматического старта всех сервисов, которые находились в активном состоянии на момент последнего завершения работы.

### 5. Мониторинг и метрики

Система реализует экспорт телеметрии для последующего сбора внешними средствами:

* **Экспорт в формате Prometheus:** На отдельном порту системы формируется эндпоинт, отдающий метрики в стандартном формате Prometheus (RPS, статус RL, доступность сервисов, потребление ресурсов). Прямая интеграция (Push-модель) не используется; Prometheus самостоятельно собирает данные по Pull-модели.

### 6. Пользовательский интерфейс

Проектируются три основные экранные формы:

1. **Главная панель управления (Dashboard):** Общий список заглушек, их текущий статус, кнопки управления (Старт/Стоп/Логи), настройка RL и просмотр назначенных адресов.
2. **Управление кластером:** Форма добавления и мониторинга Slave-хостов, отображающая их текущую загрузку и количество запущенных на них сервисов.
3. **Редактор конфигураций и журналов:** Централизованное окно для правки конфигурационных файлов сервисов и просмотра журналов исполнения (логов) в режиме реального времени.

### 7. Дополнительные механизмы (Улучшения)

Для повышения отказоустойчивости и удобства эксплуатации в проект включены следующие функции:

* **Шаблонизация параметров запуска:** Возможность создания предустановок (Templates) с наборами JVM-аргументов для типичных задач.
* **Механизм самовосстановления (Self-healing):** Автоматический перезапуск имитационного сервиса при его внезапном падении (на основе мониторинга PID).
* **Снимки конфигурации (Snapshots):** Возможность сохранения и быстрого развертывания целых групп заглушек («сцен») для различных сценариев тестирования.
* 
**Кросс-платформенная совместимость:** Тестирование и адаптация работы системы на отечественной ОС **Astra Linux**.
