Тема работы — «Разработка системы для проксирования и мониторинга имитационных сервисов в среде нагрузочного тестирования».
Научный руководитель — старший преподаватель Кружалов Алексей Сергеевич.

[Слайд 2: Актуальность]
Современные системы плотно интегрированы с внешними сервисами.
При нагрузочном тестировании использовать реальные внешние системы нельзя — они вносят непредсказуемые задержки и могут испортить продуктовые данные.
Поэтому применяют заглушки — имитационные сервисы.

На типовом стенде их одновременно работают десятки. Управлять ими вручную — неэффективно.
Готовые решения — WireMock, MockServer, Tomcat — либо слишком ресурсоёмки, либо не умеют менять параметры без перезапуска.
К тому же в условиях импортозамещения нужна совместимость с Astra Linux — ни одно из них её не обеспечивает.

[Слайд 3: Цель и задачи]
Цель — спроектировать и разработать систему централизованного управления заглушками и мониторинга их состояния.

Объект исследования — инфраструктура запуска заглушек.
Предмет — механизмы и алгоритмы автоматизированного управления.

На защиту выносятся четыре результата:
архитектура программного комплекса,
механизм динамического проксирования,
алгоритм ограничения интенсивности запросов,
методика экспорта метрик.

Для достижения цели решены шесть задач — от анализа предметной области до экспериментальной оценки.

[Слайд 4: Анализ аналогов]
WireMock и MockServer работают в виртуальной машине Java — при десятках экземпляров это существенные накладные расходы.
Tomcat требует упаковки в WAR-формат и не поддерживает динамическое изменение параметров нагрузки.
Главное: ни одно решение не умеет централизованно управлять распределённой инфраструктурой без агентов на целевых хостах.
В разрабатываемой системе хостам достаточно SSH-доступа — ничего устанавливать не нужно.

[Слайд 5: Архитектура и стек]
Выбрана монолитная архитектура с чёткой внутренней модульностью.
Микросервисы здесь избыточны — они добавили бы накладные расходы и зависимость от оркестратора.
Архитектура описана в нотации C4 Model на трёх уровнях.

Технологический стек:
Python с asyncio — асинхронная обработка запросов,
FastAPI — веб-фреймворк,
Redis в режиме AOF — хранилище с временем доступа менее одной миллисекунды.

[Слайд 6: Структуры данных]
Конфигурации заглушек, хостов и учётных записей хранятся в Redis в структурах Hash.
Это позволяет считать запись за одну операцию и обновлять отдельные поля без перезаписи всего объекта.

Бинарные артефакты хранятся только на целевых хостах.
На управляющем сервере файл существует лишь на время одной SFTP-операции — не дольше.

[Слайд 7: Топология развёртывания]
Система поддерживает два режима без изменения кода:
распределённый — один управляющий узел координирует несколько удалённых хостов,
автономный — все компоненты на одном сервере.

Взаимодействие идёт по SSH и SFTP — агенты на хостах не нужны.
Пароли хранятся в Redis в зашифрованном виде: алгоритм AES-128, реализация Fernet.
Ключ шифрования лежит вне Redis, в файле с правами 600.

[Слайд 8: Проксирование и Rate Limiting]
Прокси-модуль передаёт запрос к заглушке прозрачно: метод, заголовки и тело — без изменений.

Алгоритм ограничения интенсивности — Fixed Window Counter.
Реализован на атомарной операции INCR в Redis — корректно работает при конкурентной нагрузке, без блокировок.
Параметры лимита меняются через REST API в реальном времени, без перезапуска заглушки.
При превышении лимита возвращается код 429.

[Слайд 9: Управление жизненным циклом]
Жизненный цикл JAR и WAR-артефактов управляется централизованно.

При перезапуске системы процедура restore_state сверяет метаданные Redis с реальным состоянием ОС и автоматически поднимает упавшие процессы.
Планировщик HealthChecker обнаруживает сбой в пределах одного интервала проверки.

Метрики — двенадцать серий, включая покомпонентные задержки конвейера обработки — экспортируются в формате Prometheus.

[Слайд 10: Веб-интерфейс]
Веб-интерфейс построен на Server-Side Rendering.
Нет зависимости от внешних JS-фреймворков и CDN — система работает в закрытых корпоративных контурах.
Цветовая кодировка статусов позволяет оценить состояние инфраструктуры с первого взгляда, без чтения текста.

[Слайд 11: Функциональное тестирование]
Проведено пять сценариев функционального тестирования на Astra Linux:
перезапуск управляющего приложения,
восстановление данных после аварийного завершения Redis,
обнаружение сбоя планировщиком,
автоматический возврат заглушки в штатное состояние.

Во всех сценариях результат совпал с ожидаемым.
Статус актуализируется не более чем за тридцать секунд.

[Слайд 12: Нагрузочное тестирование]
Тестирование выполнено инструментом k6.

До 500 запросов в секунду — задержка прокси-модуля растёт линейно, не превышает 3,01 мс.
При 1000 RPS — нелинейный рост до 10,5 мс из-за насыщения пула TCP-соединений, но отказов нет.

Алгоритм Fixed Window Counter проверен при лимите 250 RPS и нагрузке 500 RPS.
Отклонение от теоретического значения — 0,13%, точность ограничения — 99,87%.

[Слайд 13: Результаты работы]
Все шесть задач решены в полном объёме.
Разработан программный комплекс для централизованного управления распределённой инфраструктурой заглушек на Astra Linux.

Научная новизна — в двух вещах:
алгоритм централизованного управления с индивидуальной настройкой rate limit для каждой заглушки,
агентно-независимая схема взаимодействия с удалёнными узлами — без установки дополнительного ПО.
