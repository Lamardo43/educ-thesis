[Слайд 2: Актуальность]
Современные информационные системы имеют большое число внешних интеграций. При нагрузочном тестировании использование реальных внешних систем нецелесообразно: они вносят непредсказуемые задержки и могут изменять продуктовые данные. Поэтому применяются имитационные сервисы — заглушки.
На типовом стенде одновременно функционируют десятки таких заглушек, и ручное управление ими становится неэффективным. Существующие решения — WireMock, MockServer, Apache Tomcat — либо избыточны и ресурсоёмки, либо не поддерживают динамическое управление трафиком без перезапуска. В условиях импортозамещения требуется также совместимость с ОС Astra Linux.

[Слайд 3: Цель и задачи]
Цель работы — проектирование и разработка автоматизированной системы для централизованного управления имитационными сервисами и мониторинга их состояния.
Объект исследования — инфраструктура запуска заглушек, предмет — механизмы и алгоритмы автоматизированного управления.
На защиту выносятся: архитектура программного комплекса; механизм динамического проксирования; алгоритм ограничения интенсивности запросов; методика экспорта метрик. Для достижения цели решены шесть задач — от анализа предметной области до экспериментальной оценки.

[Слайд 4: Анализ аналогов]
Сравнительный анализ показал, что WireMock и MockServer выполняются в виртуальной машине Java и при запуске десятков экземпляров требуют существенных накладных расходов. Apache Tomcat требует упаковки приложений в WAR-формат и не поддерживает динамическое изменение параметров ограничения нагрузки. Ни одно из решений не закрывает задачу централизованного агентно-независимого управления распределённой инфраструктурой Java-процессов — целевым хостам разрабатываемой системы достаточно SSH-доступа.

[Слайд 5: Архитектура и стек]
Архитектура — монолитная с явно выраженной внутренней модульностью. Микросервисная декомпозиция здесь привнесла бы накладные расходы и зависимость от внешнего оркестратора. Архитектура формализована в нотации C4 Model на трёх уровнях.
Технологический стек: Python с библиотекой asyncio, веб-фреймворк FastAPI, In-Memory СУБД Redis в режиме персистентности AOF — со временем доступа менее одной миллисекунды.

[Слайд 6: Структуры данных]
Конфигурации заглушек, хостов и учётных записей хранятся в Redis в структурах типа Hash, что позволяет считывать запись целиком за одну операцию и обновлять отдельные поля без перезаписи. Бинарные артефакты хранятся только на целевых хостах; на управляющем сервере файл существует лишь на время одной SFTP-операции.

[Слайд 7: Топология развёртывания]
Система поддерживает два режима без изменения кодовой базы: распределённый, когда один управляющий узел координирует несколько удалённых хостов, и автономный — все компоненты на одном сервере. Взаимодействие по SSH и SFTP исключает необходимость установки агентов на целевые хосты. Пароли SSH-учётных записей хранятся в Redis в зашифрованном виде по алгоритму AES-128 (реализация Fernet); ключ шифрования размещается вне Redis в файле с правами 600.

[Слайд 8: Проксирование и Rate Limiting]
Прокси-модуль обеспечивает прозрачную маршрутизацию: метод, заголовки и тело запроса передаются к заглушке без изменений.
Алгоритм ограничения интенсивности — Fixed Window Counter — реализован на атомарной операции INCR Redis, что обеспечивает корректный подсчёт при конкурентной нагрузке без блокировок. Параметры лимита изменяются через REST API в реальном времени без перезапуска заглушки. При превышении лимита возвращается HTTP-код 429, предотвращая перегрузку целевого сервиса.

[Слайд 9: Управление жизненным циклом]
Жизненный цикл артефактов JAR и WAR управляется централизованно. При перезапуске управляющего приложения процедура restore_state сверяет метаданные в Redis с фактическим состоянием операционной системы и автоматически перезапускает завершившиеся процессы. Фоновый планировщик HealthChecker обнаруживает сбой в пределах одного интервала проверки.
Метрики — двенадцать серий, включая покомпонентные задержки конвейера обработки запроса, — экспортируются в формате Prometheus exposition format.

[Слайд 10: Веб-интерфейс]
Веб-интерфейс реализован по технологии Server-Side Rendering и не зависит от внешних JavaScript-фреймворков и CDN, что обеспечивает работу в закрытых корпоративных контурах. Цветовая кодировка статусов позволяет оценить состояние инфраструктуры без чтения текста.

[Слайд 11: Функциональное тестирование]
Проведены пять сценариев функционального тестирования в среде ОС Astra Linux: перезапуски управляющего приложения, восстановление данных после аварийного завершения Redis, обнаружение сбоя планировщиком и автоматическое возвращение заглушки в штатное состояние. Во всех сценариях наблюдаемые результаты совпали с ожидаемыми; актуализация статуса выполняется не более чем за тридцать секунд.

[Слайд 12: Нагрузочное тестирование]
Нагрузочное тестирование выполнено инструментом k6. В диапазоне до 500 запросов в секунду сквозная задержка прокси-модуля растёт линейно и не превышает 3,01 миллисекунды. При 1000 запросов в секунду наблюдается нелинейный рост до 10,5 миллисекунды, обусловленный насыщением пула TCP-соединений; при этом отказы обслуживания отсутствуют.
При проверке алгоритма Fixed Window Counter с лимитом 250 запросов в секунду и нагрузкой 500 RPS отклонение от теоретического значения составило 0,13 процента, что соответствует точности ограничения 99,87 процента.

[Слайд 13: Результаты работы]
Все поставленные задачи решены в полном объёме. Разработан программный комплекс для централизованного управления распределённой инфраструктурой имитационных сервисов в среде ОС Astra Linux.
Научная новизна работы заключается в алгоритме централизованного управления с поддержкой индивидуальной настройки ограничения интенсивности запросов для каждой заглушки и в реализации агентно-независимой схемы взаимодействия с удалёнными узлами без установки дополнительного программного обеспечения.
