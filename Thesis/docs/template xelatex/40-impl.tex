\subsection{Требования к программно-аппаратной среде}

Развёртывание программного комплекса выполняется на сервере под управлением операционной системы Astra Linux~\cite{astra-linux, burenin-astra}. Минимальные требования к аппаратной конфигурации управляющего сервера приведены в таблице~\ref{tab:hw-requirements}.

На управляющем сервере должны быть установлены следующие программные компоненты:

\begin{itemize}
  \item интерпретатор Python версии 3.10 и выше;
  \item хранилище Redis версии 5.x с включённым режимом персистентности AOF~\cite{redis-aof}.
\end{itemize}

На целевых хостах, где исполняются имитационные сервисы, требуется OpenJDK~17 или более поздней версии~\cite{openjdk}. Установка какого-либо дополнительного программного обеспечения агента на целевые хосты не требуется: взаимодействие с удалёнными узлами осуществляется исключительно через протокол SSH.

\subsection{Установка зависимостей и подготовка окружения}

На первом этапе средствами штатного пакетного менеджера Astra Linux устанавливаются Python~3, менеджер пакетов pip, модуль виртуальных окружений \texttt{venv} и сервис Redis. Redis включается в автозагрузку и запускается.

На втором этапе создаётся изолированное виртуальное окружение Python, что исключает конфликты с системными пакетами. После его активации выполняется установка зависимостей проекта из файла \texttt{requirements.txt}. Состав зависимостей включает: FastAPI~\cite{fastapi}, Uvicorn~\cite{uvicorn}, asyncssh (SSH/SFTP-клиент), httpx~\cite{httpx}, pydantic-settings~\cite{pydantic}, cryptography~\cite{cryptography-fernet}, redis-py, а также вспомогательные библиотеки aiofiles, Jinja2~\cite{jinja2} и python-multipart.

Полные листинги команд подготовки окружения вынесены в приложение~Г.

\subsection{Генерация ключа шифрования и настройка Redis}

Для защиты паролей SSH-учётных записей применяется симметричное шифрование по алгоритму Fernet~\cite{cryptography-fernet}. Ключ генерируется однократно при первоначальном развёртывании и сохраняется по пути, заданному в параметре \texttt{FERNET\_KEY\_PATH}. Директория создаётся с правами доступа, ограничивающими чтение файла ключа только для учётной записи службы.

В конфигурационном файле Redis активируется режим персистентности AOF директивой \texttt{appendonly~yes}. Это гарантирует восстановление всех записанных операций при аварийном перезапуске хранилища~\cite{redis-aof, macedo-redis}. Дополнительно рекомендуется привязать Redis к адресу \texttt{127.0.0.1} при совместном размещении с приложением, а политику вытеснения задать равной \texttt{noeviction}, поскольку произвольное удаление ключей конфигурации недопустимо.

\subsection{Регистрация приложения как системной службы systemd}

Для обеспечения автоматического запуска при загрузке операционной системы и перезапуска при аварийном завершении приложение регистрируется в качестве системной службы \texttt{systemd}. Конфигурационный файл службы размещается в директории \texttt{/etc/systemd/system/}. Полный текст unit-файла вынесен в приложение~Г.

Ключевые директивы unit-файла:

\begin{itemize}
  \item \texttt{After=network.target redis.service} -- служба активируется только после готовности сетевого стека и хранилища Redis;
  \item \texttt{ExecStart} -- команда запуска: интерпретатор Python из виртуального окружения с аргументом \texttt{main.py};
  \item \texttt{Restart=on-failure} и \texttt{RestartSec=5} -- автоматический перезапуск при ненулевом коде завершения с паузой в 5~секунд;
  \item \texttt{User} -- учётная запись, от имени которой выполняется процесс (не \texttt{root}).
\end{itemize}

После создания файла выполняется перезагрузка демона (\texttt{systemctl daemon-reload}), регистрация в автозагрузке (\texttt{systemctl enable}) и первоначальный запуск службы. Текущее состояние и журнал службы доступны через стандартные команды \texttt{systemctl status} и \texttt{journalctl}.

\subsection{Запуск приложения и проверка готовности}

Приложение реализует ASGI-интерфейс~\cite{asgi-spec} и запускается посредством сервера Uvicorn~\cite{uvicorn}. В процессе инициализации выполняется жизненный цикл \texttt{lifespan}: устанавливается соединение с Redis, создаются экземпляры внутренних сервисов, вызывается процедура восстановления состояния (\texttt{restore\_state}), которая проверяет фактическую доступность заглушек, числившихся активными в момент последней остановки. Затем при наличии соответствующих флагов в глобальных настройках запускаются фоновые задачи -- планировщик проверки доступности хостов и сборщик журналов процессов.

После успешного запуска веб-интерфейс доступен по адресу \texttt{http://<IP>:8000}. Корректность соединения с Redis подтверждается индикатором в боковой навигации интерфейса (рисунок~\ref{fig:impl-dashboard}, приложение~В). Эндпоинт метрик в формате Prometheus exposition format~\cite{prometheus-exposition} доступен по пути \texttt{/metrics} и может использоваться для интеграции с внешней системой мониторинга~\cite{prometheus-docs, turnbull-prometheus}.

\subsection{Конфигурация целевых хостов}

После запуска управляющего сервера в разделе «Настройки» веб-интерфейса регистрируются целевые хосты и SSH-учётные записи. Для каждого хоста указываются: сетевой адрес, порт SSH, рабочая директория для размещения артефактов и учётная запись. При локальном развёртывании (адрес \texttt{127.0.0.1}) SSH-соединение не устанавливается -- операции выполняются напрямую через системные вызовы, что определяется компонентом \texttt{HostResolver}. Статус доступности хоста обновляется в рамках очередного цикла планировщика HealthChecker и отображается в интерфейсе (\texttt{OK} / \texttt{ERROR} / \texttt{UNKNOWN}).

\section{Тестирование механизмов автоматического восстановления состояний и перезапуска сервисов}
\label{sec:testing-restore}

\subsection{Цель и состав испытаний}

Данный раздел посвящён экспериментальной проверке двух взаимосвязанных механизмов системы: восстановления состояния реестра заглушек при перезапуске управляющего приложения и непрерывного контроля доступности запущенных сервисов фоновым планировщиком HealthChecker. Оба механизма обеспечивают отказоустойчивость инфраструктуры имитационных сервисов без ручного вмешательства оператора.

Для подтверждения корректности реализации были проведены следующие сценарии испытаний:

\begin{compactlist}
  \item «Холодный» перезапуск управляющего приложения при работающих заглушках (штатная ситуация).
  \item Перезапуск управляющего приложения при принудительно завершённых процессах заглушек (аварийная ситуация -- автоматический перезапуск).
  \item Перезапуск управляющего приложения после аварийного завершения Redis с последующим восстановлением данных из AOF-журнала.
  \item Обнаружение HealthChecker'ом факта аварийного завершения заглушки в штатном режиме работы (без перезапуска приложения).
  \item Проверка корректности смены статуса заглушки при устранении причины сбоя (автоматическое возвращение из \texttt{ERROR} в \texttt{RUNNING}).
\end{compactlist}

Тестирование проводилось на развёрнутом стенде под управлением ОС Astra Linux. Конфигурация стенда: управляющий сервер 8/8, на котором одновременно располагались управляющее приложение, Redis и целевые имитационные сервисы (локальный режим развёртывания).

\subsection{Сценарий 1. Перезапуск приложения при работающих заглушках}

\textbf{Подготовка.} В реестр системы зарегистрированы 2 имитационных сервиса. Все переведены в состояние \texttt{RUNNING}.

\textbf{Действие.} Управляющее приложение остановлено командой \texttt{systemctl stop mockcontrol} и запущено повторно командой \texttt{systemctl start mockcontrol}.

\textbf{Ожидаемый результат.} Процедура \texttt{restore\_state} при инициализации обходит реестр заглушек, проверяет фактическое наличие каждого процесса по сохранённому в Redis полю \texttt{pid}, подтверждает его активность и восстанавливает HTTP-клиент прокси-движка. Статусы в Redis и отображение в интерфейсе остаются \texttt{RUNNING}.

\textbf{Наблюдаемый результат.} После перезапуска все заглушки отображаются в интерфейсе со статусом \texttt{RUNNING}. Журнал службы фиксирует успешное завершение процедуры восстановления для каждого сервиса.

\subsection{Сценарий 2. Перезапуск приложения при завершённых процессах заглушек}

\textbf{Подготовка.} Аналогично сценарию~1: 2 заглушки в состоянии \texttt{RUNNING}. До перезапуска управляющего приложения процессы заглушек принудительно завершены командой \texttt{kill} по их PID.

\textbf{Действие.} Управляющее приложение перезапущено.

\textbf{Ожидаемый результат.} Процедура \texttt{restore\_state} обнаруживает отсутствие процессов (сигнал \texttt{kill~-0} возвращает ошибку либо системный вызов \texttt{os.kill(pid, 0)} выбрасывает исключение \texttt{OSError}). Для каждой такой заглушки автоматически вызывается \texttt{\_start\_mock\_from\_data} -- перезапуск с сохранёнными в Redis JVM-аргументами и путём к артефакту. Redis-запись обновляется новыми значениями \texttt{pid}, \texttt{port} и \texttt{started\_at}.

\textbf{Наблюдаемый результат.} После завершения инициализации все заглушки отображаются в состоянии \texttt{RUNNING}. В журнале службы присутствуют записи об обнаружении отсутствующих процессов и об успешном перезапуске каждого из них.

\subsection{Сценарий 3. Восстановление данных после аварийного завершения Redis}

\textbf{Подготовка.} 2 заглушки в состоянии \texttt{RUNNING}.

\textbf{Действие.} Процесс Redis принудительно завершён сигналом \texttt{SIGKILL} (имитация аварийного сбоя без штатного сохранения). Redis и управляющее приложение перезапущены.

\textbf{Ожидаемый результат.} Redis при запуске воспроизводит все операции из AOF-журнала (\texttt{appendonly.aof}), восстанавливая данные реестра заглушек с потерей не более одной секунды операций (в соответствии с директивой \texttt{appendfsync everysec}~\cite{redis-aof}). Управляющее приложение обнаруживает восстановленные данные и выполняет стандартную процедуру \texttt{restore\_state}.

\textbf{Наблюдаемый результат.} Конфигурации всех зарегистрированных заглушек, хостов и учётных записей восстановлены. Заглушки в состоянии \texttt{RUNNING} перезапущены автоматически. Данные интерфейса соответствуют состоянию до сбоя Redis.

\subsection{Сценарий 4. Обнаружение аварийного завершения заглушки планировщиком HealthChecker}

\textbf{Подготовка.} Заглушка работает в состоянии \texttt{RUNNING}. Интервал проверки планировщика установлен в значение 30~секунд (параметр \texttt{DEFAULT\_HOST\_CHECK\_INTERVAL} или настройка в интерфейсе).

\textbf{Действие.} Java-процесс заглушки принудительно завершён сигналом \texttt{SIGKILL} при работающем управляющем приложении.

\textbf{Ожидаемый результат.} В течение следующего цикла планировщика HealthChecker выполняются две независимые проверки: проверка живости процесса по PID (локальный вызов \texttt{os.kill(pid, 0)} или SSH-команда \texttt{kill~-0 PID} для удалённого хоста) и HTTP-опрос корневого эндпоинта заглушки. При отрицательном результате PID-проверки статус заглушки немедленно обновляется до \texttt{ERROR} без ожидания нескольких неудачных HTTP-попыток. Цветовой индикатор в интерфейсе меняется с зелёного (\texttt{RUNNING}) на красный (\texttt{ERROR}).

\textbf{Наблюдаемый результат.} Не позднее чем через 30~секунд статус заглушки изменился на \texttt{ERROR}. Журнал зафиксировал предупреждение «process not found».

\subsection{Сценарий 5. Автоматическое возвращение заглушки из состояния ERROR}

\textbf{Подготовка.} Заглушка находится в состоянии \texttt{ERROR} (аварийное завершение процесса из сценария~4). Оператор вручную запускает Java-процесс заглушки или использует кнопку «Старт» в интерфейсе для перезапуска.

\textbf{Действие.} Заглушка запущена штатным образом. Ожидается следующий цикл HealthChecker.

\textbf{Ожидаемый результат.} HealthChecker в следующем цикле проверки подтверждает, что PID-проверка успешна и HTTP-опрос корневого эндпоинта возвращает ответ (любой код HTTP считается признаком активности сервиса~\cite{httpx}). Счётчик накопленных HTTP-отказов для данной заглушки сбрасывается. Статус в Redis обновляется до \texttt{RUNNING}.

\textbf{Наблюдаемый результат.} Не позднее чем через 30~секунд статус заглушки сменился с \texttt{ERROR} на \texttt{RUNNING} без дополнительных действий оператора.

\textbf{Вывод.} Логика HealthChecker'а допускает проверку заглушек, находящихся в состоянии \texttt{ERROR}, что обеспечивает автоматическое возвращение сервиса в штатное состояние после устранения причины сбоя без перезапуска управляющего приложения.
